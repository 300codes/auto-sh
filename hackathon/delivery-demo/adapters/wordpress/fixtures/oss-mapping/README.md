# WP-M02 synthetic OSS mapping fixture

Every file in this directory is synthetic. No Studio command, test runner, database export, deployment or URL verification produced these files. The `passed` check records are contract inputs only; their raw reports explicitly say `executed: false`. Unit-test success does not prove application AC, preview availability, parent Progress 5.3/5.5 or a new OM→WP→OM run.

The selected future publication target is **Studio Preview**. No preview URL is included or published here. The test-only preview gate always classifies a current matching fixture observation as `fixture_not_live`; expired, unverified and wrong-build observations cannot establish live acceptance. This is preparation, not an implemented deployment-report API.

The base/result fixtures represent the same scoped site, with one added, one modified, one deleted and one unchanged theme path. The site creation attempt intentionally differs from the current task attempt. The host execution ledger correlates the current project/task/attempt/baseline/hash/profile with both tool operation IDs and an explicitly fictional `fixture-run-*` ID. Tool scope is checked against independently supplied trusted host scope and never grants authorization.

`database-surrogate.txt` contains a tiny invented string. It is **not SQLite**, a dump or private application data. Its SHA256 substitutes for a frozen database artifact solely to exercise the existing snapshot algorithm. Theme hashes, database hashes, test-definition hashes and raw-report hashes are SHA256 of the exact committed bytes. Snapshot contentHash is SHA256 of compact JSON with keys in order `{schemaVersion:1,databaseHash,themeFiles}`, sorting theme path keys lexicographically, matching `packages/delivery-wordpress/src/snapshot.ts`. It is not a Git themeCommit. Snapshot manifests have no baseCommit/resultCommit.

The test-only mapper lives beside `wordpressStudioContract.test.ts`. It produces `delivery.result-manifest/v1` then exercises the existing schema, correlation, acceptance and AC-proof functions. Add/change/delete paths are the union of snapshot theme paths with differing hashes, restricted by both task and profile. A database-only hash change changes the revision without adding a fictional theme path; this does not authorize database mutations.

Known boundary: existing OSS result correlation does not bind result workspace to base workspace. A regression explicitly documents that the current acceptance function permits a changed result workspace when checks agree. The mapper's same-site guard is local test preparation and is **not deployed API security**.

Negative coverage includes correlation/scope/ledger/revision/profile, unknown AC/test, duplicate check IDs, check revision, path restrictions/escapes, changed bytes with stale hashes, incomplete ToolChecks, failed/not_run/partial/missing proof and preview provenance. ToolCheck values (`http.local`, `studio.create`, `snapshot.capture`) never become ResultCheck evidence. Syntactically valid failed/not_run and incomplete check sets may be imported by OSS while providing no AC proof. Fixture-side proof demonstrates the pure function only and cannot set a real task to verified.
