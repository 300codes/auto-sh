## Header rules

- Lock header: `x-om-ext-optimistic-lock-expected-updated-at: <ISO updatedAt>`.
- R7 (both sources), R8 and R10 `plan_proposal` send the **project** version. The first write without it answers
  `428 optimistic_lock_required`; a stale one gets platform `409 optimistic_lock_conflict` with `currentUpdatedAt`.
- A replay of the same `manifestId` + same content (R7/R10) needs **no** header and never answers 409 for staleness.
- After every 2xx use `projectUpdatedAt` from the response as the next project version. Do not re-read the project.
- R10 `manual` needs no lock header. Task updates (R12) use the **task** version (`updatedAt` from R9 or the 201).
- Body caps: R7 8 000 000 bytes, R10 1 000 000 bytes → `413 payload_too_large`.

Flow for both inputs: FROM_BRIEF = R7 `requirements_proposal` → (design screens in the draft) → R8 requirements + design
on v1 → R10 `plan_proposal` for the **active** baseline → R8 both kinds on the merged version → tasks `→ ready`.
FROM_DESIGN = manual draft with screens + AC → R7 `manual` → R8 ×2 → R10 (`plan_proposal` or `manual`).
Every R7 write and every R10 `plan_proposal` write creates a new baseline version. Nothing edits or deletes a baseline, decision or evidence. No
PUT/PATCH/DELETE route exists for them (live: DELETE/PUT answer 404 and change nothing).

## Error codes (top `code` → typical detail codes)

| Code | Status | When |
|---|---|---|
| `unsupported_schema_version` | 422 | unknown `schemaVersion` of any manifest |
| `foreign_reference` | 422 | `foreign_project`, `foreign_baseline`, `baseline_hash_mismatch` (plan made for other content) |
| `idempotency_conflict` | 409 | same `manifestId`, other content (R7/R10) |
| `duplicate_stable_id` / `missing_acceptance_criteria` / `missing_render` / `temporary_url_only` | 422 | freezing a draft (R7) |
| `attachment_hash_mismatch` | 422 | stored bytes/size differ from the declared sha256/size |
| `hash_mismatch` | 422 | stored baseline content altered after the fact (`stored_content_altered`) |
| `baseline_not_approved` | 422 | R10 plan or task `→ ready`: `baseline_not_active`, `<kind>_decision_missing`, `<kind>_rejected`, `<kind>_decision_invalid` |
| `unknown_ac` / `unknown_test_id` / `missing_required_tests` / `path_not_allowed` / `cycle` | 422 | plan content (hallucinated AC/test, escaping paths, cycles) |
| `subject_hash_mismatch` | 409 | R8 names another hash (`subject_hash_mismatch`) or version (`subject_version_mismatch`) |
| `reason_required` | 422 | rejected decision without a reason |
| `baseline_not_active` | 422 | reserve (R14) on a task pinned to a superseded baseline |
| `baseline_mismatch` | 422 | result manifest names another baseline than its reserved attempt |
| `optimistic_lock_required` / `optimistic_lock_conflict` | 428 / 409 | header rules above |
| `forbidden` (`feature_required`, `actor_required`) | 403 | missing feature; decision without a signed-in user |
| `not_found` | 404 | other tenant/organization, archived project, random id |

## Scope-change and immutability rules (master-plan 3.1/3.2)

New file `packages/core/src/modules/delivery_os/commands/__tests__/scopeChange.test.ts`, one `describe` per rule:

1. **Append-only.** The whole delivery_os command id set is pinned. No baselines/decisions/results/evidence command
   updates or deletes, and none has an `undo`. A scan of every module `route.ts` (declarations **and** `export { … }` lists) finds no
   PUT/PATCH/DELETE on baseline, decision or result routes. No `api/<method>/` folder routes exist that could bypass
   the scan.
2. **Scope change → n+1.** After v1 is approved, a changed draft freezes v2. v1 and its decisions stay deep-equal and the
   active pointer stays on v1 until v2 has both approvals. The pinned task keeps `baselineId = v1`, and
   `taskUpdateSchema` drops any `baselineId`.
3. **Late result.** For an attempt reserved on v1 while v2 is active, a manifest relabelled with v2 id/hash answers
   `422 baseline_mismatch`. The real one is stored as evidence of **v1**. Traceability for v2 shows no task and no
   evidence of v1, even for evidence that names a v2 task. Project progress uses the v2 AC count (0 proven,
   `planning`), not v1.
4. **Reserve on superseded.** `422 baseline_not_active`, no write, no event. A task pinned to the active v2 still
   reserves (control).
5. **Decisions.** v1's hash and/or version cannot approve v2 (`409 subject_hash_mismatch`, detail per field). The second
   of two contradictory decisions on the same hash loses with `409 optimistic_lock_conflict`. There is no approval
   without a signed-in user (`403 actor_required`). Only `commands/decisions.ts` creates decisions or assigns `activeBaselineId` (source scan). The concurrent 409 is
   the project optimistic lock, so any second writer with the old version loses.
   `resolveActiveBaseline` does not approve on a single kind even a year later (no timeout approval).
6. **One schema.** Manual freeze, requirements import and plan import (chained FROM_BRIEF) all persist content that
   parses with `baselineContentV1Schema`, hashes canonically and has the same key set.

Mutation check: 7 temporary guard removals (evidence baseline, traceability filter, status filter, reserve guard,
subject check, actor check, a DELETE export on the baselines route). Each turned the suite red and was reverted. The
first run left the traceability evidence filter unproven, so a mislabelled-evidence case was added. No production file
changed.

## Limitations

- "Records cleaned up" means the smoke project is archived (soft delete). Its baselines and decisions stay, because
  they are append-only by design.
- Traceability is a pure projection. It has no endpoint yet (report/traceability API is OSS-05). Project status (R5)
  already uses the active-baseline denominator.
- The live smoke cannot reach `ready` → reserve on a fresh project without a stored render (`missing_render`), so the
  live leg of rule (4) is the `→ ready` refusal. Reserve's `baseline_not_active` is proven by unit tests.
- Real two-connection races (concurrent decisions) are simulated on a mocked EM; the DB-level race belongs to QA.
- Joint acceptance at H16 (QA-03, UI-03 confirm the approved merged baseline of both inputs) is open.
