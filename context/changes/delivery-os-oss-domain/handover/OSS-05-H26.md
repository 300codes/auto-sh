## DTOs

**DeliveryReport v1** (R22 answer, `lib/contracts.ts#deliveryReportV1Schema`, fixture
`lib/fixtures/delivery-report.v1.json`): `revision` + `revisionSource` (`selected | latest_result | none`),
`acceptanceCriteria[] { acId, status: passed | failed | not_run | missing | manual_pending, tests[], manualCheck,
taskIds }`, `rows[]` (requirement → AC → task → test / manual check → `evidenceId`, `rawReportHash`,
`deploymentEvidenceId`), `scans[] { checkId, status: present | failed | missing, reportedStatus, evidenceId }`,
`deployment { status: verified | unverified | missing, evidenceId, url, environment, buildId }`, `gates.publishable` /
`gates.releasable` `{ ok, blocking[] { kind: revision | ac | scan | deployment | deploy_decision, id, status } }`,
`decisions[] { id, kind, verdict, subjectType, subjectId, sourceRevision, decidedAt, reason, appliesToRevision }`,
`progress`, `usage[]`, `truncated`, `totalRows`.

Blocker split: `revision`, `ac` (anything but `passed` / `manual_pending`) and `scan` block **both** gates;
`ac=manual_pending`, `deploy_decision` and `deployment` block **only** `releasable`.

**Deploy decision (R20 body)**: `{ baselineId, sourceRevision, verdict: approved | rejected, reason? }` — row
`kind deploy`, `subjectType baseline`, applies only to the same revision and baseline hash.
**Release decision (R21 body)**: `{ deploymentEvidenceId, verdict, reason? }` — row `kind release`,
`subjectType deployment_evidence`, revision copied from the deployment row, applies only to that revision.

## R20 / R21 for UI-05

Both: header `x-om-ext-optimistic-lock-expected-updated-at: <project.updatedAt>`; answer `201 { decisionId,
projectUpdatedAt }` (next lock value). Features: R20 `delivery_os.deploy.approve`, R21 `delivery_os.release.approve`
(`deploy.approve` alone cannot release). A reject needs a reason and is never gate-checked.

| Code | R20 deploy | R21 release | UI meaning |
|---|---|---|---|
| `400 validation_failed` | body invalid, revision missing | body invalid | form error |
| `422 reason_required` | reject without reason | same | reason field required |
| `428 optimistic_lock_required` / `409 optimistic_lock_conflict` | lock missing / stale | same | reload report |
| `404 not_found` | project out of scope | project or deployment row out of scope | not found |
| `422 invalid_revision` | revision kind ≠ profile | stored revision kind ≠ profile | — |
| `422 baseline_not_active` | `baselineId` not active | deployment of a non-active baseline | stale baseline |
| `422 report_not_green` | `gates.publishable` false | `gates.releasable` false | show `details[]` (`path <kind>:<id>`, `code <status>`) |
| `422 unsupported_evidence_kind` | — | row is not a deployment | — |
| `422 deployment_incomplete` | — | deployment row without revision | — |
| `422 deployment_unverified` | — | deployment not verified | "verify the preview first" |
| `422 revision_mismatch` (`deploy_revision_mismatch`) | — | consent exists only for another revision | "give publish consent for this revision" |
| `422 deploy_decision_missing` (`deploy_decision_missing` / `deploy_decision_rejected`) | — | no consent, or latest is a reject | "publish consent missing" |

Check order R21 approve: verified → consent → report gate (under the project row lock).

## QA-05 recipes (TC-DELIVERY-009)

Setup once (admin@acme.com has `delivery_os.*`):

```bash
BASE=http://localhost:3100; API=$BASE/api/delivery_os; LOCK=x-om-ext-optimistic-lock-expected-updated-at
TOKEN=$(curl -s -X POST $BASE/api/auth/login -d email=admin@acme.com -d password=secret | jq -r .token)
H=(-H "authorization: Bearer $TOKEN" -H 'content-type: application/json')
ver() { curl -s "${H[@]}" $API/projects/$P | jq -r .updatedAt; }
report() { curl -s "${H[@]}" "$API/projects/$P/report?revision=git:$1" | jq '{ac:[.acceptanceCriteria[]|{(.acId):.status}],scans,deployment:.deployment.status,gates,decisions:[.decisions[]|{kind,verdict,appliesToRevision}]}'; }
```

Get `P` (project), `B` (active baseline id) and a result revision `SHA` from the manual flow
(`OSS-04-H21.md` recipes or `/tmp/t035/live.ts`: project → baseline → decisions → task → reserve → package → result).

| Case | How | Expect |
|---|---|---|
| Missing test | import a result whose manifest omits the test of AC-002 (remove the check) → `report $SHA` | `ac AC-002=missing`, publishable ✗; R20 approve → `422 report_not_green` detail `ac:AC-002` / `missing` |
| Failed test | manifest with that check `status: failed`, `exitCode: 1` | `AC-002=failed`, R20 `422 report_not_green` / `failed` |
| Skipped test | check `status: not_run` (`skipped`/`todo`/`pending` from a raw report normalise to `not_run`) | `AC-002=not_run`, both gates ✗ |
| Missing scan | manifest `dependency-audit` `not_run` and no scan evidence | `scans[0].status=missing`, R20 `422` detail `scan:dependency-audit` / `missing` |
| Scan recorded | `curl "${H[@]}" -X POST $API/projects/$P/evidence -d '{"kind":"scan","baselineId":"'$B'","sourceRevision":{"kind":"git","commitSha":"'$SHA'"},"payload":{"checkId":"dependency-audit","scanner":"npm audit","status":"passed","rawReportHash":"'$(printf d%.0s {1..64})'"}}'` | `201`, scan `present` |
| Consent | `curl "${H[@]}" -H "$LOCK: $(ver)" -X POST $API/projects/$P/deploy-decisions -d '{"baselineId":"'$B'","sourceRevision":{"kind":"git","commitSha":"'$SHA'"},"verdict":"approved"}'` | `201` when publishable |
| Unverified deployment | evidence `{"kind":"deployment",…,"payload":{"url":"https://preview.example.test","environment":"preview","buildId":"b1","deployedAt":"<iso>","uploadStatus":"succeeded","verification":null}}` → R21 with its `evidenceId`: `curl "${H[@]}" -H "$LOCK: $(ver)" -X POST $API/projects/$P/release-decisions -d '{"deploymentEvidenceId":"<id>","verdict":"approved"}'` | `422 deployment_unverified`; report `deployment=unverified`, releasable ✗ |
| Verified deployment | same with `"verification":{"status":"verified","checkedAt":"<iso>","method":"http-probe","observedBuildId":"b1"}` | R21 `422 report_not_green` while `AC-003=manual_pending`; after a human review (`{"kind":"review","taskId":"<task>","sourceRevision":…,"payload":{"verdict":"approved","summary":"ok","findings":[],"manualCheckId":"MC-visual-001","reviewer":{"kind":"human"}}}`) → `201` |
| Revision change voids consent | agent review `changes_requested`, new reserve + result → `SHA2`; `report $SHA2` | old deploy/release `appliesToRevision:false`, releasable ✗ `deploy_decision=missing`; R21 on a verified deployment of `SHA2` → `422 revision_mismatch` until a new R20 on `SHA2` |

## Limitations

- **Deployment evidence is fixture-shaped.** There is no real preview target in OSS: the caller (EXEC worker or a
  human) records the `deployment` row and its `verification`; OSS only checks that the verification names the same
  `buildId` and that upload succeeded. The URL `https://preview.example.test` in tests and smoke is not reachable.
- The release gate reads the report after the project lock; result-manifest acceptance locks only the task (known
  limit recorded in L9d), candidate for OSS-06.
- Human-only steps (publish consent, release, manual check) are enforced by features and `reviewer.kind = human` with a
  signed-in user; agents never call R20 / R21.
