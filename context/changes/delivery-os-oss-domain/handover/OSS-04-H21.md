## DTO / contract version

The contracts stay at **DTO v1** (`delivery.task-package/v1`, `delivery.result-manifest/v1`, error body v1). OSS-04 only
**added** fields and routes:

- `ExecutionAttempt` (inside `task.executionAttempts[]`): the only new field is `deliveryAttempts` (optional integer ≥ 0).
  All other attempt fields were frozen in DTO v1 (OSS-02). OSS-04 now **fills** the nullable ones: `workerRef`, `claimedAt`,
  `workflowRef`, `workflowStepId`, `dispatchedAt`, `completionDelivery` (`null | 'pending' | 'delivered'`), `lastDeliveryError`,
  `cancellationRequestedAt`, `stopConfirmation`, `reconciliation`, `resultEvidenceId`, `closedAt`, `outcome`. Strict UI
  copies must accept non-null values in them and an absent or numeric `deliveryAttempts`.
- Routes: R16 `POST /api/delivery_os/tasks/:id/results`, R17 `…/attempts/:attemptId/cancel`, R18
  `…/attempts/:attemptId/reconcile`, R19 `POST /api/delivery_os/projects/:id/evidence`.
- R19 response: `{ evidenceId, duplicate }`, plus `taskStatus` / `taskUpdatedAt` for `kind: 'review'`.
- In-process only (never HTTP): `delivery_os.attempts.reserve` with `mode: 'automatic'`, `delivery_os.attempts.claim`,
  `.link_workflow`, `.mark_delivery`, `delivery_os.results.accept` with `source: 'adapter'`, each needing
  `trustedExecution: issueTrustedExecution(actorUserId)` and a ctx without `request`. Read service:
  `createDeliveryOsAttemptQueries(em)` → `getAttempt`, `buildTaskPackage`, `listPendingDeliveries`.

## What works (OSS side)

1. **One CLI run per attempt.** A job that is redelivered after the result reaches `claim` and gets `409 attempt_closed`.
   A job that is redelivered after a restart gets `claim.changed === false` (same `workerRef`, `alreadyClaimed`). Replaying the same
   manifest answers `duplicate: true` with the same `evidenceId`, writes nothing and emits `delivery_os.evidence.recorded`
   again with the stored `completionDelivery`. After `mark_delivery failed` that value is still `pending`, so the replay
   re-signals the workflow. After `delivered` it does not.
2. **Pending delivery survives failures.** `mark_delivery failed` keeps `completionDelivery: 'pending'`, stores
   `lastDeliveryError` and counts `deliveryAttempts`. `listPendingDeliveries` keeps listing the attempt until
   `delivered`. `delivered` is idempotent (`changed: false`).
3. **A wrong baseline or foreign scope earns nothing.** A manifest built for an older/foreign baseline answers
   `422 baseline_mismatch` on the new attempt. It writes nothing, the attempt stays `claimed` without a result, and
   `proveAcceptanceCriteria` over the stored rows stays `missing` for the new baseline. Even if the same result were stored
   as v1 evidence, it would prove only v1. Foreign tenant/organization → `404`.
4. **Unknown after a restart.** The recovery scan (`listPendingDeliveries`) lists only accepted results that still
   need a workflow signal, never an attempt to run. A claimed attempt without a result is therefore never picked up for a
   new run. The executor marks it with reconcile `unknown`: in-process with `issueTrustedExecution(workerActorId)` and no
   signed-in user, or a human over R18. That sets the task to `blocked / reconciliation_required`. A claim, a result and a
   reserve with a **new** key then answer `409 reconciliation_required` until someone reconciles again. A reserve that
   repeats the **same** key and body still answers 200 with the existing attempt, and its claim is refused. Nothing is restarted.
5. **Revision-bound proof.** Evidence of a task commit A proves its AC only on A. On integration revision B, the same
   rows give `missing` with `evidenceId: null`. PASS is never carried over from task commits to the integration commit.
6. Cancel (R17) never claims that a process stopped (`stop_unconfirmed`). Stopping is confirmed only by reconcile
   `stopped` / `not_started`.

## Patch requests

**EXEC (execution bridge, `delivery_agents`), call order:**
1. `reserve` `{ taskId, idempotencyKey: stable per job, mode:'automatic', baseRevision, trustedExecution }` (ctx without `request`).
2. `startWorkflow`, park at `WAIT_FOR_SIGNAL`, then `link_workflow { workflowRef, workflowStepId, dispatched:true }`.
   `link` works on `reserved` and `claimed`, so linking before claim (as EXEC-04 requires) is fine.
3. `claim { workerRef }`. `workerRef` must be stable per worker **across restarts**; otherwise a restarted worker gets
   `409 attempt_active`. **Run the CLI only when `claim.changed === true`.** `changed:false` means the attempt was already claimed by
   this worker: it is either still running (an at-least-once duplicate job) or orphaned by a restart. In both cases do not run.
   Reconcile `unknown` only after the worker's own process table shows no live CLI for the attempt (step 6); never
   straight from this answer, because that would block a live run. `409 attempt_closed` → the result is already recorded, do nothing.
   `409 attempt_cancelled` / `reconciliation_required` / `attempt_active` → do not start.
4. The executor reads `queries.buildTaskPackage(scope, taskId, attemptId)` and runs **once**. Then
   `results.accept { source:'adapter', manifest, trustedExecution }`.
5. On `delivery_os.evidence.recorded` with `completionDelivery:'pending'`: signal the workflow, then
   `mark_delivery { outcome:'delivered' }`; on a signal failure `mark_delivery { outcome:'failed', error }` and retry later.
6. On worker start: `listPendingDeliveries(scope)` → re-signal those only. The OSS read service has **no** "list
   claimed attempts" query, so EXEC keeps its own job ledger (attemptId, taskId, pid). For every ledger entry with no live process,
   check `getAttempt(scope, taskId, attemptId)`. If it is still `reserved`/`claimed` with no result →
   `reconcile { resolution:'unknown', externalEvidence, trustedExecution }` in-process. Never re-run the CLI. If a listing
   query is needed, request it from OSS as an additive `listOpenAttempts`.

## Demo-app supervision note (Cezar's tasks in `../delivery-demo-react`)

OSS supervises the **list/filter** task and UI supervises the form task. These are the two demo-app tasks that the
agents run. After review and correction, a human merges both results into the demo repo without overwriting the other task's
changes. The final AC and scans run again on the **integration commit**, never carried over from task commits (see "Revision-bound
proof"). The merge is a human action in `../delivery-demo-react` and was not done here. The OSS side only guarantees that
evidence of task commits does not count for the integration revision.

## Limitations

- No real workflow engine: the workflow link, signal and delivery are exercised with the commands only. The resume path belongs to EXEC.
- The unit tests use an in-memory store. Real Postgres row locks, the unique-index race and a real app restart belong to QA
  (the live smoke checked restart-free behaviour over 5 s idle only).
- The recovery-scan assertion in QA (c) is structural: `listPendingDeliveries` cannot list an attempt without a result
  by design. The executor-count and `getAttempt` assertions carry the proof.
- Only `manual_handoff` can be reserved over HTTP. `automatic` is proven in-process in tests; the live smoke does not cover it.
- Scope-change scenario (b) is not in the live smoke (unit test + QA recipe).
